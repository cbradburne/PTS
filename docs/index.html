Five cameras.
One operator. Zero cables.

PTS is a five-mount motorised pan / tilt / slider / zoom camera system for live video production — wireless, self-healing, and controllable from a PC, phones, a touchscreen console, Stream Decks and QLab cue stacks.

Source on GitHub Overview PDF Companion guide

The mounts

Each mount is a self-contained four-axis robot: pan, tilt, slider and zoom (stepper or LANC) driven by a Teensy 4.1 at 600 MHz through TMC2209 silent stepper drivers. StallGuard sensorless homing means no limit switches — the mount finds its own travel ends by feel.

Motion controller

Teensy 4.1 + TeensyStep4
Smooth jog profiles with expo curves, direction reversals handled as a single continuous ramp, per-axis speed presets, 10 stored positions in EEPROM.

Wireless bridge + screen

ESP32-S3 · 1.75″ round AMOLED
Shows live state, signal, presets and stored positions; doubles as a spirit level using the onboard IMU. Touch & hold opens setup.

Safety by construction

500 ms dead-man
Jogging requires a live 20 Hz command stream. If any upstream link dies — hub, PC, WiFi — the motion controller stops itself in half a second.

The hub & its console

A single ESP32-S3 hub runs the camera network: its own WiFi access point, an ESP-NOW star to the five mounts, and simultaneous servers for every kind of controller — TCP for the PC app, WebSocket for phones, OSC for show control, USB serial, and a UART link to a 7″ touchscreen console.

Look-at tracking

The signature move: the camera keeps aiming at a fixed subject while the slider travels. Calibrate a subject once — aim at it from both ends of the rail, two taps — and the mount solves its 3D position by triangulation. From then on, pan and tilt become derived values, computed continuously from the slider position, and the shot stays locked on the presenter while the camera orbits past.

  • Eight named subjects per mount, stored in EEPROM, survive power cycles.
  • Switch subjects mid-move from any controller — the shot re-aims smoothly while the slider keeps travelling.
  • Pre-aim phase: pan/tilt settle on target before the slider starts, so the move begins composed.
  • ◀ / ▶ one-tap moves with live arrow feedback mirrored on every screen — whoever started the move.

Control surfaces

Every surface speaks to the same hub, sees the same state, and can hand off to any other mid-show. Positions and calibrations live on the mounts — controllers are stateless and interchangeable.

PC app

PyQt6 dark-theme controller: game-pad jogging with expo curves, position grid with live borders, look-at calibration wizard, computer-vision tracking (optical flow or YOLO) that drives pan/tilt while you ride the slider, connection health diagnostics, and an OSC server of its own.

Web app

Served from the hub's flash — join the CamMount WiFi and it's just there. Full position recall, jog, speeds and look-at on any phone; portrait and landscape layouts.

Hub console

The 7″ touchscreen shows five live camera tiles, drives positions and speed dials, hosts per-camera config (speeds, homing, inversion, stall tuning), and owns the pairing UI — conflicts and forget-a-mount included.

Stream Deck & cue stacks

Bitfocus Companion and QLab drive everything over OSC — recall shots, hold-to-jog, look-at moves and E-STOP from buttons, or fire camera moves as cues in the show script, in time with light and sound.

Engineering for showtime

A live rig earns trust by surviving the boring failures: radios that wedge after twelve hours, links that drop mid-jog, a mount that reboots mid-show. PTS treats reliability as a feature with a spec.

PAIRINGZero configuration

No MAC addresses in source, no per-unit builds. Mounts pick their camera number and hub on their own touchscreen; the hub binds on first contact, renumbering just works, and conflicts pop a one-tap Replace/Ignore prompt on the console. Moving the rig between venues — or WiFi channels — heals automatically.

RECOVERYSelf-healing radios

Hub and mounts each run an autonomous detect → reinit → restart ladder for the classic long-uptime ESP32 radio wedge, with boot-loop guards in RTC memory. An idle maintenance restart keeps the hub's uptime below the degradation horizon — it waits for a quiet moment, never fires mid-move.

SAFETYMotion-side dead-man

The Teensy stops any velocity move within 500 ms of its command stream going quiet — audited across every mode, including the obscure ones (zoom during a look-at move). E-STOP is one packet, from any surface, and hard-stops all four axes.

TELEMETRYHealth before symptoms

Every node — Teensys, bridges, hub, console — reports heap watermarks, worst loop time, link failures and reset cause every 10 seconds into the PC log. Slow leaks and radio degradation announce themselves hours early, with anomaly-triggered reports the moment something jumps.

PROTOCOLOne source of truth

The binary protocol is defined once in a canonical C header. A pre-commit checker verifies the Python and JavaScript mirrors and compiles the actual firmware encoders, byte-comparing them against the PC decoders — wire-format drift cannot land.

SIMULATORHardware-free development

A full hub-plus-five-mounts simulator speaks the real protocol over TCP, with a fault-injection console: link wedges, NACKs, packet loss, dead mounts. The PC app, OSC surface and UI develop against it with zero hardware on the desk.

OSC reference

Two identical servers — one on the hub (169.254.22.22:9700, no PC required), one in the PC app — accept the same address space. Point Companion's Generic: OSC connection at either. N = camera 1–5; slots and speeds are 1-based, subjects 0-based.

AddressArgumentsAction
/pts/estop—E-STOP every mount
/pts/cam/N/estop—E-STOP mount N
/pts/cam/N/gotoslot 1–10Recall a stored position at the active speed presets
/pts/cam/N/storeslot 1–10Store the current position
/pts/cam/N/clearslot 1–10Clear a stored position
/pts/cam/N/jogpan tilt slider zoomVelocities −1000…1000, re-streamed at 20 Hz until stopped
/pts/cam/N/jog/stop—Stop jogging (put on the button's release action)
/pts/cam/N/speed/pt1–4Active pan/tilt speed preset
/pts/cam/N/speed/sl1–4Active slider speed preset
/pts/cam/N/subject0–7Select look-at subject — switches live during a move
/pts/cam/N/lookat0 | 1Look-at slider move to min (0) or max (1) with the selected subject

Hold-to-jog uses Companion's press/release action pairs. Lost a release message? A 15-second TTL stops the jog anyway, and the mount's own dead-man remains the final backstop. Full recipes in the Companion guide.

Build it

Everything is in the repository: firmware for all four board types (one binary each — no per-unit configuration), the PC app, pinned Arduino libraries, STEP models and PCB fabrication files.

# compile every firmware target against the repo-pinned libraries
tools/build.sh

# run the PC app
cd pc_app && python3 -m pip install -r requirements.txt && python3 main.py

# develop with zero hardware
python3 tools/mount_sim.py

First bring-up is two taps per mount: hold its screen, pick CAM 1–5, tap your hub, save. The hub learns each mount on first contact.
