Building the firmware

Boards, pinned libraries and flashing — one binary per board type, no per-unit configuration.

There are four firmware targets. Each builds to a single binary that runs on every unit of that type — identity, pairing and calibration live in NVS/EEPROM, set from the touchscreens, so there's nothing per-unit in source.

Libraries

Arduino library versions are pinned in the repo's libraries/ folder — the versions there are the versions that compile. Board settings and the pinned versions are documented in libraries/README.md. For the Arduino IDE, copy the libraries/ folders into your Arduino libraries directory.

Command-line build

With arduino-cli installed (brew install arduino-cli), one script compiles every target against the pinned libraries — board FQBNs are baked in, so there's no Tools-menu state to get wrong:

tools/build.sh                   # compile all four targets
tools/build.sh hub display       # compile a subset
tools/build.sh flash hub [port]  # compile + upload one target

It needs the esp32 (3.x) and Teensy cores, which arduino-cli shares with an existing Arduino IDE 2.x install — so an existing setup needs nothing extra. Build output goes to .build/ (gitignored).

First bring-up

  1. Flash the hub and the mounts.
  2. Power everything up.
  3. Pair each mount from its own screen: hold ~1.5 s → pick CAM 1–5 → pick your hub → Save. The hub needs no action — it learns mounts on first contact (Pairing & identity).
Set your own WiFi credentials before deploying The hub creates the CamMount access point from an SSID and password defined near the top of firmware/esp32_hub/esp32_hub.ino. Change the SSID and especially the password to your own before using the rig anywhere real — the repo ships with a placeholder, and anyone who knows it can join your camera network.

Running the PC app

cd pc_app
python3 -m pip install -r requirements.txt
python3 -m pip install opencv-contrib-python   # + ultralytics for YOLO
python3 main.py

Then set the connection in Config. Full tour on the PC app page.

Developing with no hardware

The simulator speaks the real protocol as a hub plus five mounts, with a fault-injection console (link wedges, NACKs, packet loss, dead mounts):

python3 tools/mount_sim.py       # then point the PC app at 127.0.0.1

The simulator only serves the PC app. To bring the display and web app to life as well — for screenshots, or UI work without a rig — flash the hub's demo build instead. It invents five mounts with stored positions; recalls flash amber while "travelling" for 15 s, then settle green on arrival:

tools/build.sh flash hubdemo     # demo hub: five simulated mounts
tools/build.sh flash hub         # back to a real rig
Why this works everywhere at once The hub is the switchboard, so the simulated mounts reach the 7″ display, the PC app and the web app through the normal path — all three agree, with no changes to any of them. Demo builds never write the pairing table, so nothing persists; and power down any real mount while demoing, or its genuine identity will collide with a simulated one and raise a pairing conflict.
Protocol integrity The binary wire format is defined once in a canonical C header, and a pre-commit checker verifies the Python and JavaScript mirrors and byte-compares the compiled firmware encoders against the PC decoders — so wire-format drift can't land. After cloning, enable the hook with git config core.hooksPath .githooks.
Hardware files STEP models for the pan/tilt head and slider are in Print Files/, and PCB fabrication files are in the repo root. Detailed mechanics, BOM and wiring docs are on the way.
