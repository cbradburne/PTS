Companion / QLab (OSC)

Put shots on Stream Deck buttons and fire camera moves as cues in the show script.

PTS speaks OSC (Open Sound Control) over UDP port 9700. Point Bitfocus Companion or QLab at it and every function — recall a shot, hold-to-jog, look-at moves, E-STOP — becomes a button or a cue, in time with light and sound.

One server: the hub

The hub is the OSC server — 192.168.4.1:9700 on the hub's PTS- WiFi, or through a WiFi→LAN bridge joined to it. No PC needed: hub + console + mounts + Stream Deck is a complete rig, and both commands and feedback come from the same place.

There used to be a second server inside the PC app, on the same port and the same /pts/... namespace, and the two had drifted apart: tally and record existed only in the PC app, autofocus and zoom only in the hub. A tally button aimed at the hub was a well-formed message arriving at a server that had never heard of tally — and an unknown address is dropped in silence, which is the worst way for a control surface to fail. That server is gone and its two verbs moved to the hub.

The practical gain: the hub is always on and a laptop is not, so a tally lamp or a record cue no longer depends on anyone's PC app being open.

Tally on a Pocket Cinema Camera 4K

The /pts/cam/N/tally addresses do nothing on a Pocket 4K. Tested on the rig on 2026-08-17: three tally commands reached a paired, actively reporting camera and it neither answered nor changed. On connect that camera volunteers ISO, white balance, shutter angle, battery, transport, lens type, reel, take and operator unprompted — and has never once mentioned the tally category. A body that describes itself that thoroughly would report tally if it had it.

The addresses are kept because they are correct by Blackmagic's published spec, and a studio or URSA body — which is what the tally group is aimed at — should accept them. On a Pocket, the thing that lights the front indicator is the camera recording. So the tally you can actually drive is /pts/cam/N/record, with /pts/cam/N/recording coming back as the camera's own confirmation that it is rolling.

Connecting Companion

  1. Companion → Connections → add Generic: OSC.
  2. Set Target IP to 192.168.4.1 (the hub), and Target port to 9700.
  3. Use the connection's "Send message" actions on buttons, as below. Use integer arguments (floats are also accepted).

Direction buttons vs. the raw jog /pts/cam/N/jog takes four signed velocities and suits a fader or a stick. The named directions suit buttons: bind press → 1 and release → 0 on the same address. Any non-zero value is full deflection — a button sends 1, and treating that as a speed would creep the mount instead of moving it. Speed comes from the active preset. Each direction owns one axis, so holding left and up together gives a diagonal and releasing one leaves the other running.
Camera control /pts/cam/N/autofocus fires instantaneous autofocus on the Blackmagic camera attached to that mount, over the mount's own Bluetooth link — no SDI cable and no converter. Fire-and-forget: the Blackmagic protocol has no acknowledgement, so nothing comes back to say the lens moved, and a camera that is off or unpaired simply has the command dropped at the mount. The PC app's CC panel shows which cameras are reachable.

Each mount must be paired with its camera once, on a bench. Every mount ships with camera control built in, but pairing needs the six-digit code the camera puts on screen, typed in while someone is watching — so it cannot happen out on a rig. The bond then survives power cycles and reflashes, and it is also how a mount knows which camera is its own: with several cameras on a rig they all advertise the same way, so a paired mount goes straight to the right one and ignores the rest. A mount that has never been paired says not paired in the CC panel, distinct from camera off, because the fix is different.

To pair, hold the mount's screen to reach SETUP, then hold again for CAMERA PAIRING. The camera shows six digits; type them on the keypad. FORGET clears every camera that mount is bonded to — what a camera moved to a different mount needs. The mount is off the air while pairing, so the screen leaves on its own after two minutes.

Feedback — buttons that show the rig

The hub sends state back, so a Stream Deck can show which shot a camera is sitting on, whether a mount is online and what speed it is set to — without you tracking any of it in Companion.

Turn on Listen for Feedback in the OSC connection, then add an OSC: Listen for OSC messages (Integer) feedback to a button, matching on the address and value below.

AddressValueMeaning
/pts/cam/N/active0 / 1Mount is online
/pts/cam/N/stateintMount state — 0 is idle
/pts/cam/N/target0–10Slot being moved to, 0 = not moving to one
/pts/cam/N/speed/pt0–4Active pan/tilt preset — 0 means this mount is not there
/pts/cam/N/speed/sl0–4Active slider preset — 0 means no rail, or the mount is not there
/pts/cam/N/slot/M/state0–3Slot M — see below
/pts/cam/N/recording0/1That camera is rolling — the camera's own report, not an echo of the command
A mount that is off reports nothing to act on After 16 seconds without hearing from a mount, every one of its slots reads empty and both speed presets read 0. A speed button pressed at it does nothing — not even to the reported number, because the hub cannot pass the command on and walking its own copy would mislead the desk the moment the mount came back.

The stored positions and presets are safe in the mount's own memory and return with it. What goes away is the desk claiming they are there to press. /pts/cam/N/active says 0 alongside, for a page that wants to grey the whole camera rather than just unlight its buttons.

Slot state is one address per slot carrying one value, so a shot button can colour itself from a single feedback with nothing to combine:

ValueMeaningTypical colour
0Empty — nothing stored heredark
1Occupied — stored, mount elsewherered
2Moving — mount is on its way hereamber
3At — mount is heregreen

It is the same stored / moving-to / arrived picture the hub display and the web app show, and because it arrives as one message a button can never be caught half-updated.

A mount with no slider reports speed/sl as 0 — no preset ever uses 0 — so a button can hide or grey itself rather than showing a speed for an axis that cannot move. The hub also ignores speed/sl/… and jog/slide/… for those mounts, so a button pressed against a rail-less mount does nothing instead of walking a number that controls nothing.

Only changes are sent, so a rig at rest is silent. Everything is resent every 5 seconds regardless, and in full the first time an address speaks to the hub, so a surface that joins late or drops a UDP packet catches up on its own.

If no feedback arrives The hub replies to whoever last commanded it — the sender's IP and source port — so there is nothing to configure, but two things can silently swallow the replies. Check that Companion's Source Port is the port it also listens on, and that the Companion machine is on the same subnet as the hub. Commands still arrive across a subnet mismatch; replies cannot get back, and UDP reports no error either way. /pts/refresh is the quickest test: bind it to a button and watch whether anything lights.

Button recipes

Recall shot 3 on camera 2 — the bread-and-butter Stream Deck button:

  • Press action: /pts/cam/2/goto, int 3

Hold-to-jog pan-left on camera 1 — uses Companion's press and release action lists:

  • Press: /pts/cam/1/jog/left, int 1
  • Release: /pts/cam/1/jog/left, int 0

A shot button that shows its own state — press recalls slot 7 on camera 1, and the button colours itself from the feedback:

  • Press action: /pts/cam/1/goto, int 7
  • Feedback on /pts/cam/1/slot/7/state = 1 → red (stored)
  • Same address = 2 → amber (on its way)
  • Same address = 3 → green (arrived)

One speed button per camera — /pts/cam/1/speed/pt/inc cycles 1→2→3→4→1 on each press, the same as tapping the speed control on any screen. Add a feedback on /pts/cam/1/speed/pt to show which preset is live.

Look-at: track subject 2, slider right, camera 3:

  • Button A press: /pts/cam/3/subject, int 2
  • Button B press: /pts/cam/3/lookat, int 1 (pressing A during the move switches the tracked subject live)

Show-stopper: a big red /pts/estop (no argument needed).

QLab

QLab network cues speak OSC natively, so a camera move can be a cue in the show script. Patch a network destination to the hub or PC app on port 9700, then a cue like /pts/cam/2/goto 4 fires a recall in the cue stack, exactly in time with lighting and sound. (QLab sends numbers as floats — the server accepts that.)

Jog safety over UDP Jogs are re-streamed at 20 Hz by whichever server received them. If a release message is lost (UDP isn't guaranteed), a 15-second TTL stops the jog anyway — and the mount's own 500 ms dead-man is the final backstop. For long moves prefer goto / lookat, which are position-bounded.
