Wired hub & satellites

Putting an ESP-NOW cell on the end of an Ethernet cable, for mounts too far away to hear the hub.

ESP-NOW is short-range radio. In one room with five mounts it is ideal — no infrastructure, no association, low latency. Spread the same five across a venue and the far one starts to struggle: a mount 50 m from the hub sat at −85 dBm and spent a week dropping out. A satellite in the same room as that mount put it at −40.

A satellite is that fix. It is the same Waveshare ESP32-S3-ETH board as the wired hub, running near the mount, relaying its traffic back over Ethernet:

Nothing else in the system changes. A satellite-attached mount pairs the same way, appears in the same place, and behaves identically to one the hub hears directly — conflicts and all.

Addressing

The hub and every satellite take their wired address from DHCP. Each prints the address it was given at boot, next to its Ethernet MAC, so there is nothing to configure per unit.

Satellites find the hub by name — pts-hub.local, resolved by mDNS multicast rather than by asking a server — so a lease change on either end does not need anyone to go and edit anything.

Finding a satellite's address

The PC app logs the whole table whenever it changes, so the addresses are in comms.log without anyone going to look for them:

SATELLITES: Foyer 192.168.1.57,  Stage 192.168.1.58

The hub reports the address each satellite's TCP connection came from, so nothing has to be asked of the satellite. A satellite that has not named itself shows as SAT 3 with its address, and if the hub is too old to report addresses at all you get address unknown rather than a missing entry.

Why not just read it off the satellite? It does print the DHCP lease it was given at boot — to its own USB serial. That is fine on a bench and no use at all once the unit is rigged, which is the only time anyone needs it.
If the network only serves registered MACs There is a chicken-and-egg: you need the lease to find the board, and the board to find its MAC. A static address can be pinned in the firmware to break it, but that leaves a second place the network is configured — so register the MAC and go back to DHCP once the board is on the list.

Naming a satellite

A satellite raises its own WiFi access point called PTS-<name>, and that name is the only thing on screen when someone is choosing which cell a mount should join. Name it after the room:

SAT_NAME="Concert_Hall" tools/build.sh flash sat

Maximum 12 characters; use _ for spaces. An over-long name fails the build rather than being quietly cut short once the unit is up a pole. Unnamed, a satellite calls itself PTS-Sat-A3F2 from its own MAC — unique, so two never collide in a scan list, and honest about not having been named yet.

"Foyer" beats any serial number The person picking a satellite is standing next to the mount, looking at a list. A room name tells them which entry is the one in the room with them; an identifier does not.

How a mount picks its satellite

The mount chooses, not the hub. Each satellite's access point appears in the mount's normal setup scan alongside the hub's, and the mount joins the strongest one it recognises. Follow the usual pairing procedure — the satellite simply serves whoever turns up.

The hub learns the route by seeing which satellite a mount's traffic arrives on. Nothing is configured, nothing has to be kept in step by hand, and a mount moved to a different cell takes its route with it.

Signal strength means something different here The RSSI reported for a satellite-attached mount is its signal at the satellite, not at the hub — which is the number worth having, because it says whether that mount is well placed for the cell serving it. A mount at −40 dBm through a satellite is healthy no matter how far the hub is.

Up to six satellites can be connected at once. Each raises its own access point on its own channel, so neighbouring cells need not share one and a distant mount stops competing for airtime with the mounts near the hub.

What a satellite does not do

It is deliberately close to a dumb pipe. It reads exactly one field — which mount a message is for — and never looks at a payload. Everything else stays in the hub.

That is why a satellite needs no firmware update when the protocol grows, and why exactly one device ever transmits to a given mount, so there is no duplicate-command handling to go wrong.

The hub's own WiFi is unchanged Adding satellites changes nothing for controllers. The PC app, phones and the console still reach the hub at 192.168.4.1 on its own access point — that is the hub's WiFi, not its wired address, and it works whatever the wire is doing.
