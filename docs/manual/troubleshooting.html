Troubleshooting

Recovery, health telemetry, and fixes for the things that actually go wrong.

Safety first: the dead-man and E-STOP

Two safety behaviours underlie everything, and explain a lot of "why did it stop?" moments:

  • 500 ms dead-man — continuous jogging needs a live 20 Hz command stream. If the stream goes quiet (PC closed, WiFi dropped, hub rebooted) the mount stops that move within half a second. This is by design, across every mode. Position recalls and look-at moves are bounded, so they complete on their own.
  • E-STOP — one packet from any surface hard-stops all four axes on every mount at once, and cancels any held jog streams.

Self-healing & recovery

The rig is built to survive the boring long-run failures. You mostly won't see these working — that's the point:

  • Radio recovery — the hub and mounts each run an autonomous detect → reinit → restart ladder for the classic long-uptime ESP32 radio wedge, with boot-loop guards in RTC memory.
  • Idle maintenance restart — the hub takes a brief restart during a quiet moment to keep its uptime below the degradation horizon. It waits for idle and defers while a controller is active, so it never fires mid-move.
  • Channel self-healing — the ESP-NOW link re-negotiates if the WiFi channel changes (Pairing & identity).

Health telemetry

Every node — Teensys, bridges, hub, console — reports heap watermarks, worst loop time, link failures and reset cause every 10 seconds into the PC app's log, with an extra report the instant something jumps. Watch the log to catch a slow memory leak or radio degradation hours before it becomes a visible symptom. If a mount is misbehaving, the log's reset-cause and link-failure counts are the first place to look.

Common issues

A mount won't connect (ring not green)

  • Check it's paired to the right hub and camera number — hold the screen 1.5 s to open Setup (Pairing).
  • Confirm the hub is powered and broadcasting CamMount.
  • Moved venues? The channel should self-heal; if not, power-cycle the mount.
  • Two mounts on the same number trigger a conflict prompt on the console — resolve it there.

The PC app won't connect

  • WiFi TCP: the PC must be joined to CamMount, with the hub at 192.168.4.1:7777 in Config.
  • USB Serial: pick the right port (use Refresh); close any other program holding the port.

The web app won't load

  • Confirm the phone is on the CamMount WiFi, then browse to http://192.168.4.1 (note http, not https).
  • Some phones auto-drop a WiFi network with "no internet" — tell the phone to stay connected.

Homing stops early or pushes into the stop

  • Tune the StallGuard threshold for that axis (0 = sensitive, 255 = coarse) in Config. Stops too early → raise it; pushes into the end → lower it.

Look-at is rejected or drifts

  • Look-at needs a Set Ref this session — aim at a calibrated subject and press Ref. Moves are rejected until you do (Look-at tracking).
  • It also needs Has slider + Look-at mode on, and Find Limits run.
  • Drifting? Re-aim and press Ref again — someone may have nudged the head.

CV tracking does nothing

  • Set the right CV tracking mount in Config and make sure its video feed reaches the PC.
  • For person detection, install ultralytics — the first run downloads the model (CV tracking).

OSC buttons don't fire

  • Point Companion/QLab at the hub (192.168.4.1:9700) or the PC app machine, port 9700, and use the exact addresses in the Companion / QLab reference.
  • A jog that won't stop usually means a lost release message — the 15 s TTL and the mount dead-man will stop it; put /jog/stop on the button's release action.
When in doubt, the mounts remember Closing and reopening a controller, or power-cycling a mount, is safe — positions and calibration live on the mounts, so you won't lose your setup (How it fits together). The one session-only thing is the look-at Set Ref, which you re-do after any power cycle.
